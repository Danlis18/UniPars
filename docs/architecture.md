# UniPars — архітектура

## Коротко

```
React (Vite, Tailwind, Router, TanStack Query)
   │  Supabase JS SDK ── тільки вхід/реєстрація (Supabase Auth)
   │  fetch + Bearer JWT
   ▼
FastAPI (Python)
   api/ ─► services/ (бізнес-логіка, перевірка доступу)
              │
              ├─► repositories/  Store-інтерфейс
              │      ├─ SupabaseStore (PostgREST, service-role ключ — лише на сервері)
              │      └─ DemoStore     (у пам'яті, демо-дані; APP_MODE=demo)
              ├─► integrations/ai    провайдер-адаптер (Anthropic Claude; замінюваний)
              ├─► integrations/news  адаптери: json_api / rss / manual
              └─► storage            Supabase Storage (приватний бакет) або локальна папка (демо)
   ▼
Supabase: PostgreSQL + RLS, Auth, Storage
```

## Ключові рішення

1. **Одна реалізація бізнес-операцій — у FastAPI.** Frontend не пише в таблиці напряму. Supabase SDK на фронтенді використовується лише для Auth. Отже, правила доступу живуть в одному місці (`backend/app/services/access.py`), а RLS у Postgres — другий рубіж захисту на випадок прямого звернення до PostgREST з anon-ключем.

2. **Store-абстракція замість ORM.** Сервіси працюють з простим інтерфейсом (`select / insert / update / delete / count`) над таблицями з SQL-схеми. `SupabaseStore` транслює це в PostgREST, `DemoStore` — у словники в пам'яті. Тому та сама бізнес-логіка й ті самі тести працюють і в демо, і з реальною базою.

3. **Демо-режим чесний.** `APP_MODE=demo` вмикає демо-вхід (вибір демо-користувача), демо-дані з позначкою «ДЕМО» та локальне сховище файлів. AI в демо-режимі не імітується: без `ANTHROPIC_API_KEY` показується стан «AI ще не підключено».

4. **Мультиуніверситетність закладена в дані.** Увесь університетський контент має `university_id`. Узгодженість (предмет, тема, допис, вкладення — з одного університету) гарантують складені зовнішні ключі `(id, university_id)` у SQL і перевірки в сервісах. Членства (`university_memberships`) зберігаються окремо від профілю; один користувач може бути в кількох університетах з різними ролями.

5. **Матеріал = допис.** `material_details` має PK `post_id` → один об'єкт, одне обговорення, без дублікатів.

6. **Пояснення** — окремий тип допису (`explanation`), щоб фільтри «Матеріали / Запитання / Пояснення» були простими.

7. **Ролі.** `student`, `moderator`, `admin` — у членстві університету; `profiles.is_platform_admin` — адміністратор платформи. Роль не можна змінити через профіль: колонки ролей не входять у дозволені для користувача оновлення (RLS + тригер), змінює їх лише admin через API.

8. **Видимість.** `posts.visibility`: `university` (усі члени університету) або `group` (лише члени навчальної групи). Обмін між університетами — прапорець `universities.settings.cross_university_sharing` (за замовчуванням вимкнено, не реалізовано в UI).

9. **Файли** зберігаються в приватному бакеті `attachments` під шляхом `{university_id}/{post_id}/{uuid}-{name}`. Посилання на завантаження — короткоживучі signed URL, які backend видає лише після перевірки доступу до допису.

10. **Новини.** Для кожного університету — довільна кількість `news_sources` з типом `json_api | rss | manual`. Синхронізація: фонове оновлення + оновлення за запитом, якщо кеш застарів; дедуплікація за `(source_id, external_id)`; `last_synced_at` / `last_error` на джерелі; при помилці показуються останні отримані новини з позначкою «не оновлено».

11. **AI.** `integrations/ai/base.py` описує провайдера, `anthropic_provider.py` — реалізація. Провайдер/модель/ключ — змінні середовища. Ліміт запитів на користувача, тайм-аути, обробка недоступності. Контекст з матеріалу додається лише після перевірки доступу; користувач бачить текст контексту перед відправленням. Діалоги приватні (перевірка власника у сервісі + RLS).

## Відхилення від запропонованої схеми

- Додано `announcements` не як окрему таблицю, а як `news_items` джерела типу `manual` — одна модель для всіх новин.
- `reactions` має лише тип `useful` (кнопка «Корисно»); структура дозволяє додати інші.
- `comments.is_accepted` + `posts.accepted_comment_id` — прийнята відповідь; `posts.status` (`open|solved`) для запитань.
- `question_details` (що пробував, який крок незрозумілий) — окрема таблиця 1:1 з постом, як і `material_details`.
